# 研究選項漏修與複製指令修復（2026-11-05）

使用者提供 IMG_1870，指出研究選項／保存與檢查按鈕未做好，以及「複製 B 協作指令」沒有真的複製。承接已授權的草稿修復，更新原 HTML；正式站不部署。

## 修復前證據

- 對照同一 HTML 第3版，7,900,336 bytes，SHA256 `6819f7fd97686cd4489503fa3ca8aa51337aa3fdb4a545dd392f8f59ecbe3d2d`，程式來源498d8b6。截圖從本地附件讀取，沒有改附件。
- 上輪只對齊「內容類型／平台」；`CollaborationPanel` 研究與其他選項仍採內容自動寬度，390px研究兩按鈕實測約164.25／129.02px。保存／檢查組仍共用自動換行排列。不能將前輪格線通過擴大解讀為所有按鈕已對齊。
- 舊 `prompt()` 等待語氣讀取、任務保存及重讀後才呼叫 `copyText`。WebKit要求寫入發生在使用者手勢內，這段非同步工作存在授權失效風險。以延遲讀取／保存、要求同步手勢、拒絕舊複製途徑的瀏覽器模型重現：複製請求發出時 active=false，剪貼簿仍是「原有剪貼簿」，且沒有可手動複製的readonly欄位。
- 這是程式／模擬政策證據，不是讀過使用者iPhone剪貼簿，也不能據此斷定實機僅有此原因。未授予AI使用、保存失敗等錯誤原本只出現在頁首，也會使按鈕附近看不出原因。

WebKit依據：[Async Clipboard API](https://webkit.org/blog/10855/async-clipboard-api/)、[Bug 222262：await後寫入及Promise ClipboardItem建議](https://bugs.webkit.org/show_bug.cgi?id=222262)。

## 實際修復

- 共用模組選項改為等寬兩欄、等高、12px間距與最小48px；研究使用簡短「找研究候選／這輪先不找」，說明明示選好後由B指令交AI查找。保存／檢查按鈕用短主標與用途分兩行，不拆開「回覆」等詞。
- 主要「複製 B 協作指令」放在設定之後、次要保存／檢查之前，並使用場域主色的整列按鈕；不更動已確認八種方法與今日／週盤。
- `copyAfterPreparing` 在原點擊中啟動 Promise ClipboardItem 寫入；文字只在來源／任務成功保存後兌現。保存失敗不交出未保存文字；API拒絕則嘗試既有途徑，仍失敗會回傳明確失敗結果。
- 已保存指令再次點複製會直接寫入，沒有新的讀取／保存等待，也不新增重複任務。來源／設定或作品名稱改變後重新準備，保留既有任務來源。
- 按鈕旁顯示準備中、成功或失敗；完整文字改為唯讀可選欄位。複製受限時可直接重試、全選後用手機複製、下載或分享。AI檢查指令也有同樣的就近回復入口。應用程式不主動讀使用者剪貼簿來驗證成功。
- 舊複製fallback加入focus、選取與原焦點恢復。原回覆、正文、歷史、完成版本及預覽儲存識別均保留。
