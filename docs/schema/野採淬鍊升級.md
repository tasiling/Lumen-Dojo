# 野採淬鍊升級(規格 v1.0,2026-11-23)

把野採素材頁現有的「感觸與探索」升級為「淬鍊」:帶著逐段編號的完整原文去和
GPT 討論,貼回後由道場核對是否逐字,再由擁有者把候選存成卡片。

本文標記沿用協作慣例:【現況】指 master 上已存在的實作,【規劃】指本規格
要求新增或更動的部分,【待裁決】指尚未由擁有者決定、暫以所列預設進行的部分。

## 擁有者已裁決的原則(2026-11-21 至 11-23)

- **觀點與洞察只能出自擁有者本人。** AI 只做三件事:整理原文、出題、整理討
  論紀錄。AI 不替擁有者下結論。
- **不失真。** 討論的對象是原文本身。AI 必須逐字引用原句,不得先濃縮再討論。
- **道場現階段不內建分析。** 道場負責產生可複製的討論包、接收貼回的結果、
  分開保存各種來源。
- **各種來源分開保存。** 原文、本人原話、AI 的整理、AI 的延伸、時間與來源
  各自獨立,供日後回看自己的狀態。
- **卡片以本人原話為主體。** AI 的整理版只能當標題的起點,須經擁有者採用或
  改寫。
- **野採平常只是收。** 討論發生在擁有者開始淬鍊某個觀點的時候。
- **淬鍊的入口有兩種。** 從一個題目出發,或從某一則採集出發。
- **一輪最多帶入五則採集。**
- **歸類採半自動,目前不做搜尋。** 量還不大,多則對照由擁有者手動勾選;每一
  輪帶入與未帶入的採集都記下來,作為日後自動化的依據。
- **影片先以逐字稿當原文。** 畫面與節奏的分析留到之後。
- **「手法觀察」是獨立的卡片類型。** 只在選了「換個角度與看手法」時產生。
- **淬鍊是現有探索的升級,不是另一個功能。** 避免重複功能。

## 與現有探索的差異

【現況】`lib/dojo/captureExploration.ts` 與 `ForageCaptureInbox.tsx` 的「感觸與
探索」:

| 項目 | 現有探索【現況】 | 淬鍊【規劃】 |
| --- | --- | --- |
| 範圍 | 一次一筆素材 | 一個題目,一到五筆素材 |
| 給 GPT 的材料 | 摘錄(`excerpt`) | 完整原文,逐段編號 |
| 存回的內容 | GPT 寫的想法、主要發現、未解問題 | 逐字問答、原文引用、候選、GPT 延伸、待查證、未回答 |
| 核對 | 只檢查 JSON 格式與素材編號 | 原文引用逐字、本人原話逐字、欄位齊全、識別一致 |
| 產出 | 留在素材上的探索紀錄 | 擁有者挑選後存成卡片 |

**存量資料:** 2026-11-23 查核 DB-14,23 筆採集紀錄的 `explorationRecords` 全
部是空陣列或沒有這個欄位,現有探索功能沒有留下任何紀錄。因此直接取代,不需
要新舊並存,也沒有資料要轉換。

## 流程

1. **發起。** 兩個入口:
   - 單筆素材的詳情頁,原「感觸與探索」的位置,改為「開始淬鍊」,該筆素材預
     先帶入。
   - 採集匣清單勾選一到五筆素材後按「帶這幾則去淬鍊」。
2. **設定這一輪。** 填寫題目、可增減帶入的素材、選出題角度。沒有原文的素材
   不能帶入,並提示先補全文。
3. **複製討論包。** 道場依下節格式產生,一鍵複製。
4. **到 GPT 討論。** 擁有者說「可以收尾」時,GPT 依回傳格式輸出。
5. **貼回。** 道場解析並執行四項檢查,只指出問題,不修改內容。
6. **採用成卡。** 擁有者逐筆決定標題用原話、採用整理版或自己改寫。
7. **結束這一輪。** 記下帶入與未帶入的素材。

## 討論包與回傳格式

【規劃】已實作為純函式,見 `lib/dojo/captureRefine.ts`,測試在
`tests/capture-refine.test.mjs`。格式名稱為 `野採討論/v2`。

- 討論包五個區塊:識別、本輪題目、原文、出題角度、討論規則與回傳格式。
- 原文段落依原文自己的換行切分。存下來時已連成一行的長文,暫依句號切開,
  介面上要註明這是暫時的切法。
- 素材在一輪裡以 `C1` 到 `C5` 代稱,段落寫成 `C1-P2`。代稱只在該輪有效,
  與素材編號的對應存在該輪紀錄裡。
- 出題角度三種:先看懂他、長出我的、換個角度與看手法。
- 回傳七個區塊:識別、逐字問答、原文引用、候選、GPT延伸、待查證、未回答。
- **`野採討論/v1` 仍可讀取。** 第一版把「待查與未回答」合成一欄;讀到時全部
  歸入未回答,由擁有者自行分辨。擁有者 2026-11-22 已用第一版跑過一輪真實討
  論,確認 GPT 會照格式輸出。

討論規則的用字目前是暫用文字(`REFINE_DEFAULT_RULES`)。【待裁決】擁有者要
自己改寫,介面需提供編輯並保存規則的地方;預設先以設定值存放,不逐輪保存。

## 貼回時的四項檢查

| 檢查 | 不通過時 |
| --- | --- |
| 原文引用是否逐字 | 標出對不上的句子,顯示原文中最接近的段落 |
| 本人原話是否逐字 | 標出被改動的候選,該筆只能由擁有者自己改寫標題 |
| 欄位是否齊全、發言編號是否連續 | 列出缺少的區塊,產生可複製的補救指令 |
| 識別是否一致 | 提示這份紀錄不屬於目前這一輪,不予保存 |

段落編號或發言編號標錯、但文字逐字相符時算通過,並說明實際位置。整理版是否
加料無法由程式判斷,所以整理版一律要擁有者按下採用才會成為標題。

## 資料保存

### 淬鍊紀錄【規劃】

沿用 DB-14 知識庫加標題前綴的先例,零 schema 異動。標題 `行光淬鍊-<id>`,
`內容` 為一個 JSON:

```
{ version: 1, recordType: "refine-round", id, topic, angle,
  sources: [{ label, captureId, title, author, kind, url, paragraphCount, textHash }],
  offeredCaptureIds, status: "open" | "returned" | "closed",
  returnedAt, format, turns, quotes, candidates, extensions, toVerify, unanswered,
  checks: { quotes, words, missing, turnGaps },
  adopted: [{ candidateN, cardId }], createdAt, updatedAt }
```

- `sources` 不保存原文全文,只保存段落數與原文雜湊;原文仍以素材紀錄為準。
  重開一輪時若雜湊不同,提示原文在討論之後變動過。
- `offeredCaptureIds` 減去 `sources` 就是未帶入的素材,即歸類紀錄。
- 逐字問答可能很長。單一屬性上限 200,000 字元,超過時的處理比照逐字稿寫回
  的做法,請實作時說明。
- 查詢須以前綴限縮,不得全撈 DB-14。

素材紀錄(`CaptureEntry`)本輪不新增欄位。素材頁要列出它參與過的淬鍊,由淬
鍊紀錄的 `sources[].captureId` 反查。

### 卡片【已裁決】

擁有者已同意野採與心知閱讀共用同一種卡片,並於 2026-11-23 裁決擴充 DB-22
洞察卡片庫。下列欄位已在 Notion 建立:

| 欄位 | 用途 | 型別 |
| --- | --- | --- |
| 洞察(標題) | 一句能獨立閱讀的話 | 原有,標題 |
| 我的原話 | 逐字保存,不改寫 | 新增,文字 |
| 標題來歷 | 本人原話、採用整理版、本人改寫 | 新增,單選 |
| 類型 | 觀點、洞察、手法觀察 | 新增,單選 |
| 依據的原文 | 回應的原文句子與段落編號 | 新增,文字 |
| 出自討論 | 討論包ID與發言編號 | 新增,文字 |
| 來源採集 | 這一輪帶入的採集紀錄,可多筆 | 新增,單向關聯到 DB-14 知識庫 |
| 來源書籍 | 書籍讀次 | 原有,野採的卡片留空 |

「來源採集」是關聯欄位,寫入時要用採集紀錄(標題 `行光捕捉-<id>`)的 Notion
頁面網址,不是素材編號字串。文字欄位單段上限 2000 字,原話或原文超過時要
分段寫入。既有五張洞察卡不改動,新欄位留空;閱讀筆記的舊流程不受影響。

**存成卡片的實作【現況】**(`lib/dojo/refineRecord.ts` 的 `refineCardDraft`、
`lib/dojo/refineStore.ts` 的 `adoptRefineCandidate`):

- 挑選時決定標題來歷與類型。類型預設取 GPT 給的類型;「手法觀察」只在「換個角
  度與看手法」的一輪可選。挑選存在淬鍊紀錄的 `picks`,存成卡片後記在 `adopted`。
- **我的原話**:原話通過逐字檢查時存該句;沒通過時,改存本人在該則發言(`T<n>`)
  的完整逐字內容,不存 GPT 改寫過的句子。該則發言不是本人說的、或因長度沒有逐字
  保存時,不能存成卡片。
- **依據的原文**:`〔素材標題〕C1-P2|句子`,句子優先取回傳中逐字通過的引用,否則
  取該段原文;多段以換行分隔。
- **出自討論**:`<討論包ID>|候選#<n>|T<發言編號>|題目:<本輪題目>`。前兩段用來在
  重試時找回已建立的卡片,避免重複建卡。
- **來源採集**:這一輪帶入、目前仍存在的採集紀錄(素材編號即其 DB-14 頁面)。
- **萃取日期**填當天,**節目應用**填「未定」。**狀態、行動型態、行動化、下次回訪日
  留空**:這些屬於閱讀洞察的行動追蹤,野採卡片還沒有行動,不應被算進待行動或回訪。
- 一則候選存成卡片後,它的挑選不能再改;這一輪也不能再重新貼回,因為新的回傳會
  重新編號候選。

### 舊的探索紀錄

`explorationRecords` 欄位保留,讀取邏輯不動。「貼上探索整理結果」的入口移
除;素材若有舊紀錄,仍以「查看探索歷程」顯示為歷史。目前沒有任何素材有舊
紀錄。

## 介面

沿用野採現有的版面與蜜橙配色,不新增平行的導覽。對照用的試用版在擁有者的
Claude 帳號裡,名為「野採淬鍊模擬」;它的四個並列步驟只是為了試流程,不要
照搬成正式站的導覽。

- 淬鍊是素材詳情與採集匣清單上的動作,進行中的一輪以單一頁面或面板呈現,
  依序是設定、討論包、貼回與檢查、候選。
- 採集匣要能看出哪些素材沒有原文、哪些只取得部分、哪些原文沒有分段。
- 卡片的瀏覽不放在野採,由織光堂與道藏取用;本輪只需在淬鍊紀錄裡列出這一
  輪存了哪些卡片。

## 本輪不做

- 搜尋與自動建議相關素材。
- 查證結果的保存與顯示。擁有者已有獨立的查證流程,輸出格式為
  `野採查證/v1`,之後掛在對應的原文段落上;本輪只需保留 `toVerify`。
- 以累積紀錄分析擁有者自己的狀態。
- 影片的畫面與節奏。
- 心知閱讀改用同一種討論格式。

## 變更後三問

1. **存量資料在新邏輯下是什麼值?** 素材紀錄不新增欄位。`explorationRecords`
   維持原樣且目前全為空。DB-22 既有卡片的新欄位為空,顯示時視為「來歷不明
   的舊卡」,不補值。
2. **新路徑建立的資料,每個必填欄位是否有值?** 淬鍊紀錄建立時 `id`、`topic`、
   `angle`、`sources`、`status`、`createdAt` 必有值;題目為空或沒有帶入素材時
   不建立。卡片建立時標題、我的原話、標題來歷、類型、出自討論必有值;原話未
   通過逐字檢查的候選,標題來歷只能是「本人改寫」。
3. **空值出現時系統行為是什麼?** 回傳缺少區塊時不保存為已回傳,只顯示檢查結
   果與補救指令。候選沒有原話時不能存成卡片。素材沒有原文時不能帶入。這些
   情況都不寫入 Notion。
